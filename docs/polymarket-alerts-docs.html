Polymarket → Telegram Threshold Alerts

Prediction markets as an early-warning signal for the real world.

This tool watches Polymarket prediction markets — but not to follow the markets for their own sake. People with money at stake price in new information fast, so a sharp move in a market's implied probability is often a sign that something is happening in the world, and that news may be about to break. When a market you're watching crosses a threshold you set, you get a Telegram message — an early nudge to go look.

For instance: a sudden jump in “Strait of Hormuz traffic returns to normal by July 31” could mean the crowd is reacting to signals of de-escalation well before they reach the headlines. It’s an indication, not an oracle — markets can be thin, manipulated, or throw false signals, so treat each ping as a prompt to investigate, not a fact.

The whole thing runs on the Supabase free tier: a scheduled function wakes every 5 minutes, checks your alerts, and goes back to sleep.

At a Glance

Every five minutes, a single Edge Function wakes up, reads your active alert rules from Postgres, fetches each unique market's price from Polymarket once, and fires a Telegram message for any alert whose threshold has been crossed. Here's the whole system:

The loop is simple: load rules → fetch prices → decide → notify → persist. Each market is fetched once per tick regardless of how many alert rules watch it. State is persisted to Postgres only after a confirmed Telegram delivery.

market A Polymarket event slug. One row in the markets table. Stores the last observed probability.
alert A rule attached to a market: threshold, strategy, Telegram chat ID, expiry, and current state (armed / triggered).
threshold A probability (0.0–1.0) that the Yes price must reach or exceed to fire the alert.
strategy How the alert behaves after firing: once (terminal) or hysteresis (re-arms below a lower threshold).

Getting Started

You need a Supabase project (free tier is fine), a Telegram bot, and the Supabase CLI (v2.106+) and Deno (v2.8+) installed locally.

1

Prerequisites

Create a Supabase project at supabase.com/dashboard (free tier). Note the project ref (the subdomain in https://<ref>.supabase.co) and the service-role key (Settings → API).

Create a Telegram bot via @BotFather (/newbot) and save the bot token. Then message your bot once and retrieve your numeric chat ID:

curl -s "https://api.telegram.org/bot<BOT_TOKEN>/getUpdates" | python3 -m json.tool

Read result[].message.chat.id from the response.

2

Link and migrate

Link your local clone to your Supabase project and push the schema migrations:

supabase link --project-ref <YOUR_PROJECT_REF>
supabase db push

Then in the Supabase dashboard: Settings → API → Exposed schemas → add polymarket_alerts to the list and save. This is required — PostgREST only serves schemas that are explicitly exposed, and the Edge Function queries Postgres through PostgREST.

3

Deploy the function and set secrets

Set the Telegram bot token as a function secret, deploy, then smoke-test:

supabase secrets set POLYMARKET_ALERTS_TELEGRAM_BOT_TOKEN=<YOUR_BOT_TOKEN>
supabase functions deploy polymarket-alerts-poll
supabase functions invoke polymarket-alerts-poll --no-verify-jwt

The smoke test should return {"markets":0,"fired":0,"rearmed":0,...} — no alerts yet, but the function runs and connects to the DB successfully.

Note on the secret name

The secret is named POLYMARKET_ALERTS_TELEGRAM_BOT_TOKEN — not the shorter TELEGRAM_BOT_TOKEN. Edge Function secrets are shared across all functions in a Supabase project, so a bare name would collide with other mini-projects. See the Maintaining section for the full story.

4

Seed an alert

Copy sql/seed.sql, replace <YOUR_CHAT_ID> with your numeric Telegram chat ID, and run it against your hosted database:

supabase db query --file sql/seed.sql

The template seeds a Strait of Hormuz market alert at 80%. Adjust the slug, label, and threshold as needed. Do not commit your real chat ID to git — keep it only in your local copy.

5

Schedule it

Fill in your project ref and service-role key in a local copy of sql/schedule.sql, then run it once in the Supabase dashboard SQL Editor. It registers a pg_cron job that invokes the function every 5 minutes:

-- Enable extensions (hosted Supabase supports both)
create extension if not exists pg_cron;
create extension if not exists pg_net;

-- Store credentials in Vault (prefixed names avoid sibling-project collisions)
select vault.create_secret('https://<YOUR_PROJECT_REF>.supabase.co', 'pma_project_url');
select vault.create_secret('<SERVICE_ROLE_KEY>', 'pma_service_role_key');

-- Schedule the poll every 5 minutes
select cron.schedule(
  'pma-poll-every-5-min',
  '*/5 * * * *',
  $$
  select net.http_post(
    url := (select decrypted_secret from vault.decrypted_secrets where name = 'pma_project_url')
           || '/functions/v1/polymarket-alerts-poll',
    headers := jsonb_build_object(
      'Content-Type', 'application/json',
      'Authorization', 'Bearer ' || (select decrypted_secret from vault.decrypted_secrets where name = 'pma_service_role_key')
    ),
    body := jsonb_build_object('trigger', 'pg_cron')
  );
  $$
);

Verify the job is registered:

select jobname, schedule, active from cron.job where jobname = 'pma-poll-every-5-min';

Running unit tests locally

The pure decision logic and the Polymarket price parser are unit-tested with Deno. No Docker needed — run from the repo root:

deno test supabase/functions/polymarket-alerts-poll/

Expects 14 passing tests (decision state machine + Yes-price parser). I/O paths (network, Telegram, DB) are verified manually against the real services during deploy.

How It Works

The poll cycle

Each 5-minute tick

When pg_cron fires, it uses pg_net to make an HTTP POST to the polymarket-alerts-poll Edge Function. The function runs this pipeline in sequence:

  1. Load active alerts — query the alerts table for rows where expire_at is null or in the future, embedding the parent market in the same query.
  2. Group by market — deduplicate across alerts so each unique market is fetched exactly once, regardless of how many alert rules watch it.
  3. Fetch prices — for each unique market, call the Polymarket Gamma API. The Yes-token price is the implied probability (0.82 = 82% chance). Update markets.last_probability.
  4. Decide per alert — run the pure decide() function: (price, threshold, strategy, rearmThreshold, state) → {action, nextState}.
  5. Notify then persist — on a fire decision, send the Telegram message first; only write state = 'triggered' and an alert_log row after a confirmed HTTP 200 from Telegram.

Each market's fetch/evaluate/notify cycle is wrapped in its own try/catch so a single bad slug (e.g. a 404 from Polymarket) cannot abort the whole batch — the remaining markets still get processed.

Alerting strategies

once vs hysteresis

Each alert has a strategy field. The alerting is edge-triggered (fires on the transition from below to at-or-above the threshold) — not level-triggered, which would re-fire every poll while above the line.

once (default)

Fire the first time the price reaches or exceeds the threshold, then become permanently terminal. No re-arm path exists. Completely immune to flip-flop spam.

Use when: a market resolves once — you want a single heads-up, not repeats.

hysteresis

Fire on crossing, then re-arm only after the price falls back to or below a lower rearm_threshold. The deadband (e.g. fire at 80%, re-arm at 70%) absorbs oscillation — the same principle a thermostat uses.

Use when: you want repeat alerts without spam when the price oscillates around your threshold.

The two strategies share a single two-state machine. once is hysteresis with the re-arm transition removed:

Reliability invariant

Send before persist

State is only persisted after a confirmed Telegram delivery. A duplicate alert (sent but state-flip failed, so it retries on the next tick) is strictly better than a silent miss (state flipped to triggered but no message was ever sent — permanent, never corrects).

If Telegram returns a non-200, the alert's state stays armed and the function retries naturally on the next 5-minute tick. If a Polymarket fetch fails, that market is skipped for this tick with no state change. All failures resolve to a missed tick, never to a permanently wrong state.

Data model

Three tables, one schema

All tables live in the polymarket_alerts Postgres schema, isolated from other projects sharing the same Supabase instance:

markets
One row per watched Polymarket slug. Stores the last observed last_probability and last_polled_at. A market is an observed fact — its price is whatever it is. Polled once per tick, regardless of how many alerts watch it.
alerts
A rule + notification target layered on a market. Key columns: threshold (0.0–1.0), strategy (once/hysteresis), rearm_threshold (hysteresis only), telegram_chat_id, expire_at (null = never expires; past = inactive), and state (armed/triggered). One market can carry many alerts.
alert_log
An audit row written each time an alert fires. Records alert_id, probability at time of firing, and triggered_at. Written only after confirmed Telegram delivery.

Why It's Built This Way

These are the non-obvious design decisions. Each has a rule (what was decided) and a reason (why). Read these before changing anything structural.

Architecture

Platform choice

  • Supabase over AWS Lambda for compute + scheduling + state. A single platform handles all three: pg_cron for scheduling, Edge Functions for compute, Postgres for state. The free tier (500K invocations/month) far exceeds the ~8,600/month a 5-minute poll needs. AWS Lambda + EventBridge + DynamoDB also works, but spreads the system across three services for no benefit at this scale.
  • Vercel was rejected for the scheduling/polling job. Its Hobby (free) plan caps cron frequency at hourly — too slow for a useful threshold alert. Vercel is still the intended host for the web-app frontend in Phase 2; it just cannot own the poll loop.
  • A scheduled poll, not an always-on server. The workload is "check N markets every 5 minutes." A cron-triggered serverless function serves this at zero idle cost; a long-running process would burn a free VM doing nothing between ticks.
  • The Supabase project is shared, not dedicated. The free tier caps active projects at 2. Isolation is by Postgres schema. See the Namespacing card below.
Data model

Markets and alerts are separate tables

  • Markets and alerts are split even though Phase 1 has a single event. One market can carry many alert rules (different thresholds, different users). Separate tables mean each unique market is polled once per tick rather than once per rule. Done now, while the DB is empty, to avoid a painful migration later.
  • The notification channel (telegram_chat_id) is NOT factored into its own table. There is exactly one channel type (Telegram) and one recipient. A channels table is YAGNI until multiple channels or recipients exist — splitting it now would add a join and buy nothing. This marks the deliberate boundary of the decoupling.
  • A single nullable expire_at replaces a separate is_active flag. is_active = false and "past expiry" are two ways to express the same "don't poll this" state, which is confusing. One expire_at expresses both time-bound auto-expiry and manual kill (set it to now()). A reversible pause is a web-app-phase need; it will use a future status enum rather than reintroducing two overlapping on/off fields.
Infrastructure

Shared Supabase project namespacing

  • Multiple mini-projects share one Supabase project, isolated by a Postgres schema. The free tier allows only 2 active projects. A separate database within the project was rejected because Supabase's tooling (PostgREST, supabase-js, Edge Functions, the dashboard) only connects to the single postgres database — a second database would be unreachable. A schema is the only workable isolation boundary, and drop schema ... cascade cleanly removes a whole mini-project.
  • Every project-global Supabase namespace is prefixed per mini-project. Edge Function names, Edge Function secrets, Vault secret names, and pg_cron job names are all shared across the entire Supabase project. This project uses: function polymarket-alerts-poll, secret POLYMARKET_ALERTS_TELEGRAM_BOT_TOKEN, Vault secrets pma_project_url / pma_service_role_key, and cron job pma-poll-every-5-min.
  • A custom schema must be added to the API's "Exposed schemas" list. PostgREST only serves exposed schemas. The Edge Function reaches Postgres through PostgREST via supabase-js, even when using the service_role key. Without exposure, deployed function queries fail with a schema-not-exposed error.
Integration

Polymarket integration scope

  • Phase 1 supports binary Yes/No events only. A Polymarket event can contain multiple markets (outcomes), and handling multi-outcome events means deciding which outcome's price to watch. That complexity is out of scope until there's a concrete need; binary events cover the driving use case.
  • The Gamma API returns outcomePrices as a stringified JSON array, not a real array. The value must be parsed before use. A parse failure is treated as a fetch failure (skip this market this tick) rather than a crash. This is a non-obvious gotcha that looks like clean JSON until it isn't.
  • The Yes-token price IS the implied probability. A price of 0.82 means the market implies an 82% chance. The threshold compares against this directly — no conversion needed.

Maintaining It

Project structure

File tree

supabase/ ├── config.toml # exposes polymarket_alerts schema to the API ├── migrations/ │ └── …_create_schema.sql # schema + 3 tables + grants └── functions/polymarket-alerts-poll/ ├── index.ts # orchestration: load → fetch → decide → notify → persist ├── decision.ts # PURE once/hysteresis state machine (unit-tested) ├── decision_test.ts # Deno unit tests for decision logic ├── polymarket.ts # Gamma API fetch + tested Yes-price parser ├── polymarket_test.ts # Deno unit tests for the parser ├── telegram.ts # send message + build alert text └── db.ts # schema-scoped Supabase queries sql/ ├── seed.sql # template: insert a market + alert (placeholders) └── schedule.sql # template: pg_cron + Vault wiring (placeholders) docs/superpowers/ # design spec + implementation plan

Key responsibility boundaries: decision.ts is pure logic (no I/O), fully unit-tested. polymarket.ts has a pure parseYesProbability (tested) and an I/O fetchYesProbability (manually verified). index.ts is the glue — it owns the send-before-persist ordering and per-market error isolation.

Namespacing gotchas

Shared-project collision points

Warning: token collision risk

Edge Function secrets are shared across every function in the Supabase project — they are not scoped per function. If a sibling mini-project added to this shared Supabase project sets a secret named TELEGRAM_BOT_TOKEN (without the POLYMARKET_ALERTS_ prefix), it would silently overwrite the token for every function, including this one. Your alerts would stop firing with no obvious error. Always use the full prefixed name POLYMARKET_ALERTS_TELEGRAM_BOT_TOKEN for this project.

The same collision risk applies to all project-global namespaces. Keep these names consistent:

NamespaceName used
Postgres schemapolymarket_alerts
Edge Functionpolymarket-alerts-poll
Function secretPOLYMARKET_ALERTS_TELEGRAM_BOT_TOKEN
Vault secret (URL)pma_project_url
Vault secret (key)pma_service_role_key
pg_cron jobpma-poll-every-5-min

Scheduling SQL is a one-time run

vault.create_secret errors on a duplicate name. On a re-run, skip the two create_secret lines or use vault.update_secret instead. The committed sql/schedule.sql contains only placeholder values — never commit real project refs or service-role keys.

Known limitations

Consciously deferred follow-ups

These were surfaced by a holistic code review and are non-blocking but worth knowing before extending the code:

  • Terminal once+triggered alerts are still loaded every poll. loadActiveAlerts filters only on expire_at, so a fired once alert is re-fetched and re-evaluated to noop each tick, and its market is still polled even if no live alert needs it. Harmless at small scale. A future optimisation: add a filter so terminal alerts drop out — verify against a real DB first, as there are no DB-integration tests.
  • decide() returns nextState but the orchestrator ignores it. recordFire/recordRearm hardcode the target state, which matches nextState on every current path. If a third state is ever added, wire nextState through instead of hardcoding.
  • Alert message links to polymarket.com/event/${slug} using the market slug. For binary events the event and market slugs coincide (true for the seeded Strait of Hormuz market), but they can differ for multi-outcome events. Revisit with multi-outcome support.
  • buildAlertMessage does not HTML-escape label. Safe now (labels are operator-set via seed.sql). Add escaping when the web-app phase lets users supply labels, since parse_mode: "HTML" would break or allow injection on </&.

Deliberately deferred to Phase 2 — do not build now

direction field (above/below threshold), reversible pause via a status enum, multi-channel notifications, multi-user auth, cooldown/debounce/nag strategies, multi-outcome (non-binary) market support.
